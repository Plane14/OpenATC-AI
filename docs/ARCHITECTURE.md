# Current Rust architecture

## Crew, missions and traffic

`core::crew_request` validates a closed JSON object with up to eight mapped aircraft actions, six cabin services and an optional cross-check. `engine::crew` waits for simulator acknowledgements and produces one combined response, including partial failures. `engine::memory` keeps bounded request/result history for each role; merely asking for a control never establishes success. `engine::cabin` models passenger activity separately from observed aircraft controls and carries unresolved mission incidents into crew context.

`core::missions` owns the versioned TOML format and limits. `engine::missions` loads validated catalogues off the session lock, runs phase/probability/choice transitions, and exposes the editor endpoints. `ui::missions` supplies a form and raw TOML view. Story choices never grant ATC permission. Media fields are retained for future playback. An explicit emergency declaration pauses training penalties and optional spacing requests; it does not invent a diversion route. See [mission authoring](../missions/README.md).

`core::traffic` owns geometry; `engine::traffic` observes bounded TCAS histories at 1 Hz, predicts taxi conflicts and provides conservative approach spacing for supported jets. Runway holds take priority over ordinary taxi conflict holds. Go-arounds for an imminent runway conflict can preempt ordinary speech. Traffic conversation uses identified targets and timestamped simulator weather; a touchdown report is retained until the aircraft is observed clear of the runway. `plugin::traffic` optionally sets the native AI count, yields to another provider, and leaves X-Plane's AI flight models enabled. Custom CSL traffic scheduling and rendering are not implemented.

`core::parking` derives stand size from loaded aircraft data and rejects occupied or unconfirmed stands. `engine::parking` rechecks during taxi-in. If occupancy changes it holds the aircraft, waits until stopped and issues a new route/readback to a suitable clear stand. Runway crossings remain separate permissions. Static scenery aircraft are not enumerable through the current TCAS feed.

`engine::initiative` offers optional direct-to shortcuts after a configurable quiet interval. Offers require known terrain clearance, no skipped restrictions and sufficient descent distance. Acceptance uses the normal amendment handler; it is not immediate route permission. `engine::squawk` assigns one simulated octal code per flight and avoids recently assigned and common special codes.

## Request interpretation and local inference

`engine::intent` decodes model classification into a closed request vocabulary. Unknown fields, invalid values and model-supplied authorization/readback evidence are rejected. Original pilot text remains available to the controller's readback checks. `server::json_mode` constrains generated syntax to a JSON object; it does not replace the engine's semantic validation or grant simulator control.

Voice discovery is refreshed from the configured provider, including before controller requests. Controller pools are intersected with the real roster and language setting; an empty custom pool uses the provider's allowed voices. Persisted identities are retained while their voice remains available, and new controllers prefer unused voices. Changing TTS providers can invalidate prior assignments.

Kokoro and Kitten share ONNX device selection in `tts::device`. A model-specific warm-up catches accelerator failures that occur after session creation and selects CPU before readiness. The LLM and STT have separate CPU overrides and initialization fallback. The independent AI server remains deployable off the simulator computer; recognition still runs in its owned helper process. See [AI server details](AI_SERVER.md).

The Rust workspace owns the deployed Linux plugin and companion engine. The earlier top-level C++ implementation and CMake build have been removed; shared regression fixtures remain. The engine owns plan, staged clearances, transcript, settings, controller roster and loaded airports. Network/model calls occur outside the shared state lock. The plugin transports telemetry and UI actions over local HTTP and uses the X-Plane SDK only on the simulator thread.

The plugin starts a detached local engine with its simulator PID. A joined background worker sends wall-clock heartbeats every two seconds independently of flight-loop pause. Disable requests local shutdown. A plugin-owned engine exits after its host disappears or heartbeats expire, with startup grace. Manually started engines and remote AI/STT/TTS services are separate and remain running. Plain plugin transport avoids bringing TLS libraries into X-Plane; the engine proxies provider requests.

`EngineClient` publishes immutable `Arc<State>` snapshots. Parsing happens outside the UI mutex; rendering clones the handle rather than the transcript and routes. The command worker and polling worker are independent. Simulator telemetry uses a single replaceable slot, so a slow model request cannot queue stale positions. Generation checks discard responses started before a flight reset. Static airport bounds, node lookup and ILS beams are rebuilt on airport load, not on each map draw.

`core::escort` advances an optional follow-me vehicle along the acknowledged taxi polyline. A cached distance table supports movement without route searching at every frame. It remains before the route limit and stops for pause or pending readback. `plugin::follow_me` resolves X-Plane's installed scenery vehicle, uses one object instance and updates at 20 Hz only while active. Other flight logic remains at 2 Hz. It uses no AI aircraft slot and does not control native traffic. Object resolution/loading happens once per session; drawing and SDK placement still require simulator acceptance.

Audio uses native device enumeration with cached IDs. Linux prefers PulseAudio/PipeWire and excludes monitor sources from capture; ALSA is a fallback. Playback honours WAV sample rate and role gain. Dataref discovery supports numeric scalars/arrays; the vendored X-Plane wrapper fixes an inverted type-mask test. The A20N ToLiss profile supplies power/radio references and standard writable COM1 tuning.

The shared UI supports simulator and desktop rendering. Local Frequencies and the airport search have independent state. Selecting a frequency queues COM1 tuning. Taxi loads scenery runways, curved pavement, taxi graphs and stands; approval is distinct from route calculation. Map arrows and opt-in terrain-following SDK instances use the approved network path. Unverified stand connectors do not receive ground arrows. Terrain footprints are probed on the SDK thread; unsafe/discontinuous surfaces are skipped. Night textures make arrows visible without adding scenery illumination.

Arrival loads the destination independently. Planned geometric descent ends at the selected landing threshold; current descent uses live vertical speed and true-ground-track closure. Incremental cached terrain probes provide centre-line ground, corridor envelope and a horizontal highest-known-ground-plus-2,000-ft reference. Missing samples remain gaps. Regional transition altitude and a published ILS initial-final altitude are references, not a computed transition level or fully constrained STAR/VNAV path. The airport browser ILS beam also depends on available published glide-angle data.

Speech is open data under `speech/`: global crew files, common ATC material and regional IFR/VFR/shared material. Recursive loading validates metadata and unique IDs. `profile.toml` longest-prefix routing selects a phraseology variant; folder scopes prevent IFR/VFR and regional leakage. Neutral phrases are shared. Entries are examples, not an operational procedure database. Crew prompts and `/suggest` consume examples; normal requests use staged controller logic; initial departure clearance/start/pushback wording is rendered from checked TOML entries with live slots. `/suggest` returns a proposal without applying a plan effect. The plan currently lacks flight-rules state, so that API defaults to IFR unless supplied explicitly.

`Slots.extra` supplies context beyond the legacy slots. New values include their spoken units. Checked rendering refuses missing context; illustrative prompt values are never live facts. Compiled system rules constrain `/suggest`; editable controller, crew and classifier prompt files load on restart. See [speech editing](../speech/README.md) for scopes, schema, references and boundaries.

Current navigation/scenery, verified controller state and aircraft-specific procedures must determine operational eligibility. A new TOML phrase cannot implement separation, runway crossings, CPDLC, emergency response or an aircraft action. Country/FIR and airport procedure review remains separate from coarse phrasebook routing. See [validation](VALIDATION.md) and [remaining work](ROADMAP.md).

The shared `core::stations` module indexes enabled scenery in priority order, resolves frequency reuse to the nearest receivable airport and supplies the same horizon/service-cap model to the UI and request gate. Service caps are Delivery/Ground 25 NM, Tower 50 NM, ATIS 100 NM, Approach/Departure 150 NM, further limited by the geometric horizon with a 10 NM airport floor. Published controller coverage volumes are loaded from installed ATC data and exposed in the developer Map tab. Reception and sector ownership are separate tests; terrain shielding and a complete remote-transmitter model are not implemented. Water/heliport-only station coverage remains incomplete because the airport geometry loader currently requires land runways.

`plugin::weather` alone queries airport surface locations via SDK 4.0 on the main thread. Timestamped samples feed `engine::radio`; online planning weather cannot flow into live ATIS. The UI serialises ATIS with other speech and cancels it through the Rust audio worker on reception changes. The request gate is unconditional even where legacy realism settings would bypass frequency checks. Network waits do not hold the session lock; reception is checked again immediately before a controller decision. Optional model wording retains deterministic decisions and accepts only unchanged operational tokens.

The Rust audio and HTTP/client workers now support cancellation during pending synthesis/transcription and state/command requests. Audio workers are joined before freeing their backend context; client workers are joined before plugin unload. This prevents delayed ATIS from playing after retuning and avoids freeing resources underneath active workers.

Channels also reads published controllers from enabled scenery `atc.dat` files and the active custom/default ATC navdata. Tower controller definitions replace scenery Tower frequencies; Ground/Delivery remain from airport scenery. Approach and Center discovery uses published horizontal coverage plus a simulated 150 NM regional network reception margin. Assigned controller altitude bands do not prevent tuning from the ground; actual transmitter locations and terrain shielding remain unmodelled. Center rows show “Sector coverage” rather than a misleading distance to a polygon centre. No controller or frequency is invented; regional transmitter locations and terrain shielding are not modelled.

Airport capabilities are assigned after ATC indexing and before optional user overrides. Clearance is handled by a published Delivery station, otherwise Ground, otherwise Tower. Where no Ground is published, Tower handles ground duties. Primary station names and frequencies remain unchanged. Separate services still require tuning the appropriate controller. The SDK `sim/atc/com1_tuned_facility` exposes the primary tuned role, not a complete combined-duty list.

IFR clearance messages omit routine teaching prompts, while readback validation checks NATO callsign/destination, route, altitude, squawk and runway. Unclear values receive a correction without granting permission. Taxi instructions remain pending until readback is accepted. Holding recognition uses the route limit, painted holding-line geometry and approach-side marker; it does not require the aircraft to stop before initiating a handoff. Protected runway edges are excluded; an intervening runway ends a partial route without crossing permission. The UI registers a native system clipboard backend for external text-field copy/paste, with persistent ownership. Live simulator voice and clipboard interaction remain user acceptance checks.

Live controller responses, readback prompts/corrections, taxi instructions, ATIS/weather wording, crew fallback replies, copilot callouts and traffic exchanges come from `speech/runtime/responses.toml`. Regional and crew example libraries provide further wording context. Runtime alternatives preserve named fact placeholders; startup rejects missing responses or changed placeholder contracts. Phrase edits do not change Rust authorization logic. Taxi readback uses structured taxiway/hold-short facts, so editable wording is not parsed as route data. An isolated engine regression edits the TOML acknowledgment and verifies that exact edited text is returned; invalid placeholder alternatives are rejected.

ATC Auto Reply sits beside Replay ATC. It submits a complete pilot readback using the active IFR/taxi clearance, or acknowledges start-up/pushback approval once. It excludes exchanges addressed to background traffic. It is disabled when no reply is pending. Pilot reply wording is editable in `speech/runtime/responses.toml`; operational values and authorization remain in Rust. Click a chat message to open a read-only selectable text box; use Ctrl+C for a selection or Copy message for the whole line.

Taxi loading prefers published scenery ATC graphs. When absent, it derives an unnamed graph from solid/enhanced painted centerlines (apt.dat styles 1/7/51/57), samples Bezier curves and intersects connected lines. Pavement gaps, edge markings and hold barriers do not become ordinary taxi links. The UI identifies this fallback. Fallback stand connectors are limited to 35 metres of continuous pavement; hold-line buffers allow room ahead of the aircraft reference point.

A holding point away from the departure threshold ends the ordinary taxi route and requires separate Tower backtrack clearance. Request runway backtrack becomes available while stopped at that route endpoint. At airports without a taxiway graph or holding point, Tower can issue runway taxi/backtrack to the assigned departure end over verified pavement and the selected runway centerline. Ground must hand the request to Tower; no specific airport is hardcoded. Backtrack clearance requires readback, grants no takeoff permission, and the arrows stop when the aircraft reaches the end. Backtrack routes reject other-runway crossings, disconnected pavement and overlap with another runway. Ordinary taxi routes stop before an intervening runway; a separate crossing clearance and readback authorise that crossing. Simulator-reported runway occupancy and final-approach protection are implemented; traffic ownership and full separation remain future work.

At the final departure hold, the engine checks the actual tuned airport station. Ground hands off to the published Tower frequency. Tower requires a ready report/check-in and clear runway checks before takeoff permission. Missing traffic data keeps the aircraft holding. Pausing, radio power off, untuned channels and other airports cannot trigger departure. Holding for traffic is reconsidered when the runway clears. Routes needing backtrack or another runway crossing retain their hold restriction and require further explicit permission. Scenery-owned runway guard lights remain unchanged; no per-holding-point native lighting control has been established. TCAS targets omit ownship and do not include traffic hidden from X-Plane’s traffic interface; this is not full traffic sequencing or wake separation.

## Window appearance

`ui::widgets` draws the header icons as vectors with consistent scaled strokes. `Interface` keeps navigation and window actions in one row when space allows, otherwise places navigation on a second row. Settings keep their own wrapping section tabs. The header reserves space for every action, including developer controls and the native pop-out button. Disabled icons inherit the ImGui alpha; pop-out is independent of the ATC-only collapse control.

Settings use visible wrapping tabs with first-run connection guidance. The theme palette lives in `ui::theme`, with one cached palette for each Light/Dark mode. The selected palette is applied while drawing; the interface scales and chooses expanded/collapsed opacity independently. Text and controls retain their own opaque colours. Copilot tuning has one visible setting that updates both legacy tuning keys for compatibility.

Engine connectivity and simulator-data acceptance are separate states. A successful state poll keeps the connection alive even when a sample is rejected. The client retains that error until a newer sample is accepted, and only accepted submissions advance the telemetry revision used to gate controller requests. Empty polls cannot acknowledge unsent data. Optional instrument readings are filtered at the simulator boundary; invalid required coordinates and motion still reject the sample without replacing the last accepted flight state. Errors include the field and value.

The plugin draws a standard translucent ImGui background. It does not capture simulator scenery or run background post-processing passes. The opt-in desktop capture in `desktop::review` checks layout only; it is not native X-Plane acceptance or an FPS benchmark.

## New flight and lifecycle

The header's New flight action clears flight-specific engine and UI state while retaining settings, phrase history and controller voices. A generation counter rejects responses started before the reset. The plugin clears its crew callbacks and guidance caches when notified; simulator controls are not restored or changed by reset.

Importing a plan after a finished flight uses the same engine reset. Importing while parked keeps the current crew exchange and selected mission. Transmission sequence numbers remain monotonic so a new plan cannot reuse an old message ID.

Disable stops the flight loop, heartbeat and local interface. The SDK window and renderer are retained for re-enable, so there is only one active ImGui context. Enable rebuilds simulator bindings and resumes the companion connection. Plugin commands and its menu are registered once. The remote AI server is independent of this lifecycle.

## Requests and continued monitoring

`core::traffic::profiles` validates the versioned aircraft, airline and hub tables and selects compatible aircraft/operators from a stable seed. `engine::traffic_profiles` loads bundled and personal overrides on the bounded worker pool, caches the validated set, and retains the last good set after a rejected edit. `POST /traffic/profiles` returns profiles and diagnostics. This service does not yet create or move a generated fleet.

CPU-heavy scenery/navigation loading and CSL indexing share a lazy bounded Rust worker pool in `engine::workers`. It uses OS threads on Linux, Windows and macOS, with a bounded input queue and asynchronous result channels. Dropped requests skip queued work; existing session/root generation checks reject obsolete results. HTTP and simulator callbacks never wait synchronously for these workers. The configured worker count applies at engine startup; `/health` reports the active count. This pool is groundwork for generated traffic, not evidence that a CSL movement controller is finished.

`core::traffic::advisory` computes relative motion from observed targets. `engine::traffic::advisories` owns the radio lifecycle: issue, sighting report, update and closure. A missing feed is never reported as safe separation. The optional traffic-radio switch controls background pilot reports, not advisory eligibility. Sighting reports do not clear another pending readback or implicitly grant visual separation. `core::traffic::csl` indexes installed package metadata and matches aircraft/operator/livery; all parts must exist within the CSL folder. Unhandled texture overrides are rejected rather than displayed with an incorrect livery.

Advisories retain at most 63 encounters keyed by surveillance identity, callsign and station. Reused surveillance slots cannot inherit a sighting report. `Transmission::information_only` keeps advisory exchanges separate from operational instructions; all pending-readback selectors use `is_controller_instruction()`. Urgent calls run before the ordinary busy-radio gate, with runway go-arounds taking priority. They cancel prepared copilot playback but preserve the accepted clearance and its outstanding readback. Prepared replies now record generation, transmission sequence and frequency. The UI supplies the sequence on completion; stale completions cannot consume a newer pending reply, and retuning invalidates a prepared transmission.

`core::traffic::wake` contains FAA aircraft-pair departure intervals and approach spacing; `engine::traffic::wake` observes liftoffs and threshold passages. The plugin supplies optional `simulationSeconds` from the simulator flight-time dataref. Pausing and clock discontinuities cannot age away wake protection. Departure events are bounded to 64. The observer accounts for close parallel runways and displaced landing thresholds, and retains an observed approach spacing violation after touchdown. Aircraft footprint projection is shared by runway occupancy, crossing completion and arrival runway-exit monitoring. This is still incomplete for intersecting flight paths and preceding low/missed approaches.

`core::traffic::motion` is the movement foundation for generated traffic. It compiles bounded geographic segments, validates continuity and climb/descent performance, and maintains at most 63 aircraft with explicit resource ownership and per-segment permission. Reset generations reject stale work; pause and clock jumps cannot move an aircraft through a clearance limit. It publishes complete pose snapshots. It is not connected to a live fleet or CSL renderer yet: airborne continuation/holding, acceleration, turn geometry, route construction and worker publication remain required before enabling it for users.

The workspace boundaries remain appropriate: `core` owns deterministic permissions and geometry; `engine` owns HTTP, provider calls and the session; `plugin` owns SDK access; `ui` renders snapshots and sends actions. Speech TOML controls wording and examples, not permissions or runway safety. Aircraft TOML maps third-party controls, not dialogue.

Surface monitoring is now isolated in `crates/engine/src/surface.rs`, alongside the existing airborne flow in `flight.rs`. The HTTP route delegates telemetry handling to this module. `TaxiClearance::stage()` provides one derived lifecycle view without changing saved JSON: idle, awaiting readback, taxiing, crossing, at hold and crossing complete. Pending readback takes precedence over movement monitoring. A new onward clearance replaces the old crossing geometry and begins its own readback cycle.

`discipline.rs` arms the optional taxi-deviation reminder only after displacement and consecutive moving telemetry samples following readback. Movement evidence and its warning timer belong to one taxi-clearance sequence. Runway-entry protection is independent. Taxi-assistance questions retain their route, transmission and controller/frequency identity; short answers cannot acknowledge another instruction. Accepted assistance uses the existing surface router from the stopped position and issues a replacement pending readback. The router still enforces intermediate runway holds and parking suitability/occupancy. This implements revised routing, not continuous progressive-taxi directions; see the [FAA ground-movement procedures](https://www.faa.gov/air_traffic/publications/atpubs/ATC_html/chap3_section_7.html).

| Request or event | Current handling | Continued monitoring |
| --- | --- | --- |
| IFR clearance | Checked plan and explicit readback | Clearance remains pending until matched |
| Start-up/pushback | Approval and one-use acknowledgement | Aircraft action belongs to the crew/SDK flow |
| Taxi/backtrack/crossing | Explicit clearance and matched readback | Position, holding point, runway occupancy and traffic availability |
| Runway vacated | Next taxi instruction; no readback-correct reply | Position must establish that the crossing is complete |
| Holding point | Ground-to-Tower handoff or Tower runway checks | Retry when blocking traffic clears |
| Weather/position/radio check | Information reply | No movement permission or readback cycle |
| Airborne handoff/arrival | Published station and phase handling in `flight.rs` | Separate from surface route tracking |

This table documents implemented behaviour, not a complete worldwide ATC procedure model. Further work should extend deterministic permissions and tests before adding speech examples. Keep route geometry, permissions and monitoring separate from LLM wording. A single enum for all ATC requests is not introduced here: the crew, surface and airborne workflows have different state and external effects.

## Workspace layout and build scope

`crates/` is the source root; each crate has its own standard `src/` directory. A second top-level `src/` tree would duplicate that organisation. The default Cargo members are core, engine, UI and plugin. Optional desktop preview and AI/STT/TTS services remain explicit build targets. The local path dependency graph has no cycles; core has no UI, SDK, audio or network dependency.

`aircraft/`, `speech/`, `prompts/` and the root TOML files hold editable product data. `assets/` contains shipped resources. `xtask/` contains the Rust build, install and integration tools; `tests/fixtures/` contains shared data and crate-local tests exercise their owning modules. `vendor/` contains maintained dependency patches. `target/`, `build/`, `packages/` and `stage-wayland/` are generated or local directories covered by ignore rules.

The remaining large files are `ui/pages.rs`, `engine/routes.rs`, `core/airport.rs` and `core/apply.rs`. Split them by responsibility as those areas change: UI pages, provider/HTTP endpoints, scenery loading versus routing, and clearance handlers. Avoid moving unrelated code merely to reduce file length. Keep surface monitoring in `engine/surface.rs`, airborne flow in `engine/flight.rs`, and permission/readback logic in core; phrase wording cannot change those permissions.

The optional **Holding point marker** setting highlights the current route limit on the taxi map and places an illuminated translucent amber circle on simulator ground. It is off by default, independent of taxi arrows, and uses the route endpoint with the shared 45-metre stopped-aircraft detection radius shown on the map. Nearby scenery holding-line detection remains an additional recognition path. The ground marker requires an acknowledged taxi clearance, stays at the hold and disappears for crossing or takeoff permission. It is plugin guidance, not a scenery stop bar. Terrain probing follows the taxi-arrow placement checks.

Channels now checks loaded airport pavement/runway containment before using simulator reference-point proximity. Channels also loads the planned airport geometry for verification. The holding circle uses a single textured quad with a 256-pixel alpha mask instead of segmented fill/rim geometry.

Debug mode adds a `>>` header button for surface test jumps. Next holding point requires an acknowledged taxi route; departure runway start requires takeoff clearance and loaded departure scenery. Jumps follow the stored geometry, preserve gear clearance using terrain probes, stop motion, align heading and set the parking brake. They do not grant ATC permission or jump to airborne phases. Standard writable X-Plane position controls are used; third-party aircraft reposition behaviour needs simulator testing.

Outgoing controller transcript/speech messages include the flight callsign via an editable TOML addressing wrapper when it is not already present. Controller decisions and raw API result messages remain unchanged. Surface holding monitoring is restricted to Taxi/TaxiIn; departure clearance cannot send an acknowledged flight back to Delivery.

Copilot radio replies now originate in the simulator after its speech queue drains, rather than being applied inside the engine request handler. The same endpoint handles onward taxi instructions and takeoff acknowledgements. Automatic tuning and cockpit actions wait for playback and pending copilot replies. Final holding-point telemetry does not invent a pilot ready report; holding recognition no longer requires zero taxi speed. Channels also loads local airport geometry (page 6) to identify the occupied airport. Regression checks cover deferred readback, takeoff acknowledgement, moving holding detection and installed KLAX positions; live ToLiss audio timing still needs simulator testing.

Radio turn-taking uses a two-step copilot exchange: record and play the readback, then apply it after playback finishes. Telemetry marks the radio busy during playback, recording or pending crew replies, delaying automatic surface and airborne calls. A previously reported ready aircraft can receive takeoff clearance after blocking traffic clears. Crossing eligibility follows holding-point detection without a conflicting stopped-aircraft gate. Unknown runway status produces an explained standby instruction and retries when confirmation becomes available. The debug header uses a vector fast-forward icon with the same dimensions as other controls. Unit and engine regressions cover prepared readbacks, occupied-radio suppression, moving hold recognition and traffic-clearance retry; embedded simulator layout and live audio need user verification.

ATC quick requests follow the live flight phase and the published duties of the receivable tuned controller, including combined duties. ATIS and untuned frequencies do not expose controller requests. In flight, **Check in with controller** sends the tuned station name, callsign and current altitude using editable speech TOML. Crossing and landing requests are included when appropriate.

Typed ATC requests add missing controller and callsign addressing. Spoken transmissions retain the words recognized by speech-to-text. AI intent recovery tolerates clear request-word typos and recognition errors; operational values and readback checks remain authoritative. Crew requests can contain up to eight explicit actions, such as “remove chocks and external power.” Clauses inherit the action verb where appropriate. All targets are validated against the aircraft profile before the batch becomes visible to the simulator; each action needs confirmation, and failure cancels the remaining actions. Duplicate controls and unsupported clauses are rejected. The LLM can return a bounded actions array using mapped control IDs, never raw simulator refs. Settings → Voices → Pilot (own transmissions) → Speak my transmitted requests enables synthesized playback of the pilot requests. It is off by default. Engine regression tests use mocked model responses and simulator acknowledgements; live control effects remain a simulator check.


The engine proxies voice discovery through `/speech/voices` to the configured TTS service's `/v1/voices`, retaining its language metadata for selection and synthesis filtering. The UI refreshes when the service changes and supports manual refresh. The `englishVoicesOnly` setting applies to both controller assignment and speech requests. Turning it off preserves the selected international voice; the speech text remains English.

`/debug/map` is gated by developer mode. It serves the same indexed controller polygons used by the flight logic, plus a separate scenery-priority airport marker index so airports without frequencies can appear. The UI requests a viewport around the aircraft or pan centre. Shared polygons are drawn once, and markers outside the visible region are skipped. Airport identifiers and service abbreviations are expanded only for synthesis; transcript storage is unchanged.

The debug Map has no terrain sampler. The slow overlay was removed; airport markers can still be hidden independently of controller boundaries. The separate Arrival profile retains its bounded terrain sampler. The engine's station catalogue caches airport names for destination speech and named clearance readbacks.

A completed runway crossing is distinct from its report. When copilot replies are enabled, surface monitoring retains the crossing route until the copilot's prepared vacated report finishes playing and is committed. That commit calculates the next taxi leg and its pending readback. Manual mode can continue from physical crossing completion without requiring a second readback acknowledgment.

## Airborne instructions and published restrictions

`core::navigation` separates SimBrief planned altitudes from installed CIFP restrictions. Selected SID, STAR and approach records add exact, minimum, maximum and window restrictions to matching imported fixes. Runway transitions are filtered; changing a procedure reloads its installed restrictions. Explicit route step-climb markers remain planned levels until ATC issues a clearance.

`engine::instructions` tracks straight route legs, issued headings, IAS assignments and approved lateral deviations. Crossings use interpolation between telemetry samples. Off-route vectors require a known installed MORA corridor; missing cells produce a position/intention query instead of a guessed safe heading. MORA is a conservative grid reference, not local minimum vectoring altitude. Curved, unnamed and radar-vector procedure legs do not yet have a complete lateral path interpreter.

Regional handoffs use current and thirty-second predicted coverage, including altitude bands. Reception alone does not establish ownership. Outstanding readbacks block subsequent instructions and handoffs; an unanswered exchange receives a reminder after 45 seconds. Requested climbs are checked against the remaining imported route and a nominal three-degree descent with ten nautical miles reserved for final approach. The check also considers the next published crossing window when strict constraints are enabled. It does not model aircraft-specific descent performance, winds or ATC traffic separation.

Approach and landing permissions are distinct. Final alignment, installed procedures, Tower check-in and observed runway traffic feed automatic arrival instructions. Unknown traffic does not establish a clear runway. A continue-approach instruction is not permission to land. Full worldwide procedure handling, missed-approach routing and aircraft-specific performance remain incomplete; simulator acceptance is still required.

Repeated unresolved corrections keep the assigned clearance active. The legacy `terminateAfterWarnings` settings key now enables an assistance prompt alongside the correction; it does not withdraw IFR service. Explicit pilot cancellation and actual runway-conflict responses remain separate operations.

Operational phrase alternatives live in `speech/runtime/responses.toml`; airborne style examples live in `speech/common/ifr/atc_airborne_monitoring.toml`. Alternatives must retain the same declared facts. Turning LLM variety off keeps speech within the TOML phrases; turning it on allows validated natural wording. Adding an example never grants a movement permission.

Phraseology references: [FAA altitude and crossing clearances](https://www.faa.gov/air_traffic/publications/atpubs/atc_html/chap4_section_5.html), [departure restrictions](https://www.faa.gov/air_traffic/publications/atpubs/atc_html/chap4_section_3.html), [radar vectors](https://www.faa.gov/air_traffic/publications/atpubs/atc_html/chap5_section_6.html), and [controller coordination](https://www.faa.gov/air_traffic/publications/atpubs/atc_html/chap2_section_1.html). Regional wording still needs refinement outside the current FAA/ICAO example coverage.

## Model installation and radio updates

`engine::traffic_models` downloads the publisher's Bluebell DDS archives on an asynchronous worker and extracts them on the blocking worker pool. The UI polls progress; neither the draw callback nor the simulator flight loop performs network or archive work. ZIP paths and expanded sizes are checked. Installation uses a staging directory and receipt, preserves a previous installation until replacement succeeds, and retains completed downloads for retry.

COM1 reception uses the same aircraft dataref as tuning. A confirmed manual selection supersedes an outstanding copilot tuning instruction and clears the request search. The UI retains the latest simulator telemetry over delayed engine snapshots. Radio commands wait until that telemetry reaches the engine, and rejected telemetry is reported instead of silently showing a connected state. Airport service capabilities are grouped once by airport; station discovery no longer scans the entire catalogue for every airport or reads duplicate scenery entries.

## Shared LLM boundary

`engine/llm.rs` owns the single LLM transport, response decoding, common spoken-reply checks, bounded history formatting and prompt assembly. Actor handlers supply configuration and live facts, then retain their specific permissions, outcome verification, fallback and reset checks. Typed JSON interprets requests; it never grants operational authority.

`prompts/prompts.toml` supplies role instructions; `prompts/interaction.toml` supplies shared context, service descriptions and explicit fictional-example framing. Selected speech TOMLs provide examples of behaviour and phrasing, not fixed replies or current facts. The engine combines these with recipient-specific history and observations. Legacy txt mirrors remain for older integrations. Shared instruction text is runtime-editable in `prompts/interaction.toml`; missing keys retain bundled TOML defaults. Rust contains request assembly and safety checks, rather than actor instruction sentences.
